## 수정한 처리

1. 잔액만으로 위험자산 이동 가능성·수급의 질·개별 투자자의 레버리지 비율을 판정하던 문구를 수정했다. 실제 잔액 방향과 확인이 필요한 해석을 구분한다.
2. 조회 시각, 1D/5D 시작·종료일, 5D의 다섯 공표구간 기준을 표시한다. MMF형 CMA 등 포함 관계 때문에 네 잔액을 합산하지 않음을 표시한다.
3. 정상적인 공개 API 요청으로 직접 조회한다. 브라우저 설치·자동화 숨김 설정을 제거했다. 같은 주소에 한해 일시적인 네트워크/5xx/408 오류를 1회 재시도한다. 거부·리디렉션·잘못된 JSON을 우회하지 않는다.
4. 실제 응답 바이트(base64), 텍스트, 해시, 요청 인자, 단위, 조회 시각, 실제 checkout SHA를 아티팩트에 보존한다. 별도 Python 검증기가 원응답에서 기간·금액·MMF 설정원본 선택·공식 일일 증감을 독립적으로 재계산한다.
5. 최종 본문에서 각 수치·부호·방향·날짜·경보 기준을 재검사하고, 전송 직전에도 원자료와 본문 검사를 다시 수행한다.
6. 대기열 이후 최신 main과 실제 발송 상태를 읽는다. 상태가 없거나 손상됐으면 초기값으로 바꾸지 않고 차단한다.
7. Telegram 응답의 양의 정수 ID, 봇, 수신 대상, 실제 반환 본문과 서버 시각을 검사한다. 검증된 전송 영수증에 본문/원자료 해시·코드 SHA·실행 ID를 저장한다. 성공한 전송만 기준 상태에 반영하고 더 최신의 날짜·영수증을 덮어쓰지 않는다.
8. 원값이 같으면 확인된 해석 정정을 버전당 한 번만 발송하도록 한다. 강제발송 기본값은 false이고 날짜·원자료 검사를 우회하지 않는다.

## 검증과 한계

- 로컬 실제 공식 응답 18개 수집 → 독립 원자료 재계산 → 해석 생성 → 최종 본문 검사를 통과했다. Telegram을 보내거나 운영 상태를 변경하지 않았다.
- 문구 27개, 원자료 16개, 상태 반영 6개, 전송 응답 6개, 기존 상태 무결성 9개 시나리오와 숫자 자료형·달력 검사를 통과했다. fixture는 실제 값의 정제본으로, 과거 원 응답 바이트를 그대로 보존한 자료는 아니다.
- 원격 CI와 새 운영 코드의 실제 수집은 해당 Actions 기록으로 별도 확인한다. 새 코드의 자연 발송·영수증·중복 억제·예약 연속성은 이후 운영 증거가 있어야 완료로 판정한다.
- GitHub 예약은 실제 생성 지연·공백이 관측됐으나 원인은 아직 확정하지 못했다. 코드 변경만으로 예약의 정시 생성이나 100% 무오류를 보증하지 않는다.
- MMF/CMA 날짜는 요청 인자와 공식 최신일 metadata에 연결된다. 응답이 날짜를 별도로 반환하지 않는 과거 단일일 조회까지 독립적인 외부 자료로 증명한 것은 아니다.
- Telegram 응답 유실 또는 성공 후 상태 저장 전 중단은 완전한 원자적 전송을 보증할 수 없다. 기준 상태가 저장되지 않으면 다음 운영 실행에서 다시 후보가 생길 수 있다. 이 경우 후속 점검은 재실행을 추가하지 않고 실제 영수증·아티팩트와 저장 상태를 먼저 대조한다.
